# 731迭代需求 PRD文档

---

## 一、变更背景

本期迭代新增**代发订单管理模块**和**标准对外API**，实现代发订单在供应商门户独立展示，并提供供应商自动化对接能力，支持供应商自主拉取订单、回传物流信息的闭环流程。

**API设计原则**：采用**统一接口 + 订单类型区分**方案，通过 `order_type` 字段（NORMAL/DROPSHIP）区分采购订单和代发订单，公共字段共用，类型字段按需必填。供应商只需对接一套接口，降低接入成本。

---

## 三、功能详细设计

### 3.1 供应商门户-代发订单菜单

#### 3.1.1 功能概述

在现有供应商门户菜单结构中，新增「代发订单」一级菜单，与「采购订单管理」平级。

#### 3.1.2 菜单结构

```
供应商门户
├── 工作台
├── 商品管理
├── 采购订单管理
└── 代发订单（新增）
```

#### 3.1.3 权限控制

| 角色 | 权限说明 |
|------|----------|
| 供应商 | 只能查看归属自己供应商的代发订单（按供应商编码过滤） |
| 管理员 | 可查看所有供应商的代发订单 |

### 3.2 代发订单列表页

#### 3.2.1 功能概述

代发订单列表页采用**二级层级结构**展示：
- **一级（子订单维度）**：展示子订单基础信息及关联的订单收件人信息
- **二级（商品维度）**：展开后展示子订单内的商品明细

#### 3.2.2 数据来源

| 数据来源 | 说明 |
|----------|------|
| 来源系统 | 订单履约平台-拆单管理 |
| 筛选条件 | 仓发地 = 「海外仓」 |
| 数据隔离 | 按供应商编码过滤，每个供应商只能看到自己的订单 |

#### 3.2.3 状态Tab

状态Tab位于筛选条件下方，与列表在同一卡片内。

| Tab | 说明 | 子订单状态 |
|-----|------|-----------|
| 待接单 | 供应商已分配，等待确认接单 | 待接单 |
| 待发货 | 供应商已接单，等待发货 | 待发货 |
| 已发货 | 供应商已回传物流信息 | 已发货 |
| 已取消 | 订单已取消 | 已取消 |

#### 3.2.4 筛选条件

| 筛选项 | 类型 | 说明 |

### 3.4 标准对外API设计（统一接口方案）

#### 3.4.1 设计原则

采用**统一接口 + 订单类型区分**方案：
- 统一接口路径：`/api/v1/orders/*`
- 通过 `order_type` 字段区分订单类型（NORMAL/DROPSHIP）
- 公共字段共用，类型字段按需必填
- 供应商只需对接一套接口，降低接入成本

**订单类型枚举**：

| 类型 | 说明 | 对应业务 |
|------|------|----------|
| `NORMAL` | 普通采购订单 | 供应商 → 我方仓库（需要入库、质检） |
| `DROPSHIP` | 代发订单 | 供应商 → 终端客户（直接发货） |

#### 3.4.2 接口清单

| 序号 | 接口名称 | 接口路径 | 适用类型 | 功能说明 |
|------|----------|----------|----------|----------|
| 1 | 订单列表 | `GET /api/v1/orders` | NORMAL / DROPSHIP | 查询订单列表（支持筛选、分页、排序） |
| 2 | 订单详情 | `GET /api/v1/orders/{order_no}` | NORMAL / DROPSHIP | 获取单个订单完整信息 |
| 3 | 确认接单 | `POST /api/v1/orders/{order_no}/confirm` | NORMAL / DROPSHIP | 确认接单 |
| 4 | 订单发货 | `POST /api/v1/orders/{order_no}/shipping` | NORMAL / DROPSHIP | 上传物流信息（采购订单支持部分发货） |
| 5 | 订单拆单 | `POST /api/v1/orders/{order_no}/split` | 仅 DROPSHIP | 供应商拆单（代发订单专用） |
| 6 | 缺货申请 | `POST /api/v1/orders/{order_no}/out-of-stock` | 仅 NORMAL | 发起缺货申请（采购订单专用） |

#### 3.4.3 接口详细设计

**公共规则**

> 以下规则适用于所有接口，各接口特有规则在接口内单独说明。

**公共前置条件**

| 条件 | 说明 |
|------|------|
| 认证通过 | 请求Header携带有效的API Key和签名（X-Api-Key、X-Signature、X-Timestamp） |
| 数据隔离 | 供应商只能操作自己的订单，系统根据API Key自动过滤 |

**公共后置条件**

| 条件 | 说明 |
|------|------|
| 状态同步 | 所有写操作（接单/发货/拆单/缺货）成功后，状态变更同步至订单履约平台 |
| 操作日志 | 所有写操作记录操作日志（操作人、操作时间、操作类型、备注） |

**公共异常错误码**

| 错误码 | 说明 | 处理方式 |
|--------|------|----------|
| 400 | 参数错误（格式错误、必填项缺失等） | 检查请求参数格式和完整性 |
| 401 | 认证失败（API Key无效、签名错误、时间戳过期） | 检查API Key和签名算法 |
| 403 | 无权限（API Key未绑定供应商或订单不属于当前供应商） | 确认API Key绑定关系 |
| 404 | 资源不存在（订单号不存在） | 检查order_no是否正确 |
| 500 | 服务端异常 | 稍后重试或联系技术支持 |

#### 3.4.4 认证机制

**认证方式**

采用 **API Key + Secret** 认证方式，每个供应商分配独立的API Key和Secret。

**认证流程**

```
1. 供应商在门户申请API Key和Secret
2. 供应商使用Secret对请求参数进行签名
3. 供应商在请求Header中携带API Key和签名
4. 服务端验证API Key有效性
5. 服务端使用对应的Secret验证签名
6. 验证通过，返回数据
```

**请求Header**

| Header | 说明 | 示例 |
|--------|------|------|
| X-Api-Key | 供应商的API Key | `ak_xxxxxxxxxxxx` |
| X-Signature | 请求签名 | `a1b2c3d4e5f6...` |
| X-Timestamp | 请求时间戳（秒级） | `1721644800` |
| Content-Type | 请求体类型（POST请求） | `application/json` |

**签名规则**

签名步骤：
1. 将请求参数按字母顺序排列，拼接成字符串
2. 在拼接字符串末尾追加Timestamp
3. 使用HMAC-SHA256算法，以Secret为密钥，对拼接字符串进行加密
4. 将加密结果转为16进制字符串，即为签名

签名示例：
```
请求参数：
  status=pending_shipment
  page=1
  page_size=20

Timestamp：
  1721644800

待签名字符串：
  page=1&page_size=20&status=pending_shipment1721644800

签名结果（HMAC-SHA256）：
  a1b2c3d4e5f6...
```

**错误码**

| 错误码 | 说明 | 处理方式 |
|--------|------|----------|
| 401 | API Key无效 | 检查API Key是否正确 |
| 401 | 签名验证失败 | 检查签名算法和Secret |
| 401 | 时间戳过期 | 检查时间戳与服务器时间差不超过5分钟 |
| 403 | 无权访问该订单 | 检查订单是否归属当前供应商 |
| 404 | 订单不存在 | 检查订单号是否正确 |
| 400 | 请求参数错误 | 检查请求参数格式 |
| 429 | 请求频率超限 | 降低请求频率 |

**安全规则**

| 规则 | 说明 |
|------|------|
| 时间戳有效期 | 请求时间戳与服务器时间差不超过5分钟 |
| 签名算法 | HMAC-SHA256 |
| Key管理 | API Key和Secret在门户申请，支持重置 |
| 访问日志 | 记录所有API调用日志（供应商、接口、时间、IP） |
