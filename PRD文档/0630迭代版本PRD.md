## 变更背景

当前供应商信息无法同步到易仓ERP，入库通知单供应商取值全部默认为"默认供应商"，Shopify订单导出字段不足以支撑运营全链路需求，批量导入仅支持单大类，采购订单入库状态判定逻辑不够准确，POD商品需求生成方式需要优化。本次迭代打通供应商同步链路、优化取值逻辑、扩展导出字段、支持多大类导入、调整状态判定逻辑、优化POD需求生成方式。

## 功能2：入库通知单供应商取值优化

### 变更说明

原逻辑：入库通知单同步到易仓采购单时，供应商全部默认为"默认供应商"

新逻辑：

| 场景 | 取值规则 |

### 业务规则

| 编号 | 规则描述 |
| --- | --- |
| R2-1 | 报错在入库通知单推送时拦截，非易仓侧处理后回传 |
| R2-2 | 供应商名称匹配规则为精确匹配 |

### 异常处理

| 场景 | 处理方案 |
| --- | --- |
| 供应商名称存在空格/特殊字符差异 | 精确匹配，不匹配则拦截报错，提示"供应商名称不匹配，请核实"，不走默认供应商 |

## 功能4：批量导入商品多大类支持

### 涉及页面

供应商门户 - 商品管理 - 创建内部商品需求页

### 变更说明

原逻辑：批量导入仅支持单个大类，一次导入一份模板一个Sheet

新逻辑：支持选择多个大类，下载模板时自动生成多Sheet的Excel文件，每个Sheet对应一个大类，Sheet列字段根据该大类的销售变体动态生成

### 页面交互变更

**下载模板弹窗：**

| 字段名称 | 变更类型 | 说明 |
| --- | --- | --- |
| 大类选择 | 由单选改为多选 | 支持选择多个大类，无数量上限 |
| 下载模板按钮 | 逻辑变更 | 根据选中的大类，查询每个大类的销售变体，生成多Sheet的Excel模板 |

**Sheet命名规则：** 按大类名称命名，如选中"女装"和"鞋类"，生成的模板包含两个Sheet：`女装`、`鞋类`

**每个Sheet的列字段：** 按该大类的销售变体动态生成（与现有单大类模板逻辑一致），固定列：参考SKU ID、SKC、SKU、供应商SPU ID、供应商SKU ID

### 业务规则

| 编号 | 规则描述 |
| --- | --- |
| R4-1 | 大类选择由单选改为多选，无数量上限 |
| R4-2 | 下载模板时，根据选中的大类逐一查询销售变体，每个大类生成一个Sheet |
| R4-3 | Sheet名称 = 大类名称 |
| R4-4 | 每个Sheet的列字段根据该大类的销售变体动态生成（复用现有模板生成逻辑） |
| R4-5 | 导入预览时，外层按大类名称分Tab展示预览结果，每个Tab内展示该大类的全部数据（含异常标注），不需要正常/异常/异常原因子Tab |
| R4-6 | 预览阶段如任意大类Tab存在异常数据，整体拦截，不允许导入 |
| R4-7 | 导入成功后，按每个Sheet内的SKU行逐条导入到货品池（复用现有导入逻辑） |

### 异常处理

| 场景 | 处理方案 |
| --- | --- |
| 上传文件中Sheet数量与选择的大类不匹配 | 预览时拦截，提示"上传文件与所选大类不匹配" |
| Sheet名称与大类名称不一致 | 预览时拦截，提示"Sheet【{名称}】无法匹配所选大类" |
| 某个Sheet存在异常数据 | 整体拦截，不允许导入，在对应大类Tab中展示异常数据及异常原因 |

## 功能5：采购订单入库状态判定优化

### 涉及页面

供应商门户 - 采购订单

### 变更说明

原逻辑：需求单SKU状态变更为"已完结"后，通过**需求数量 vs 实际入库数量（入库-退货）**比较判定状态

新逻辑：直接通过**需求单SKU状态**判定采购订单状态，不再比较数量

### 状态变更

"部分入库/已退货"改名为**部分入库**。

### 判定规则

当采购订单关联的需求SKU状态变更为"已完结"（排除"已终止"）时，触发采购订单状态判定：

| 需求单SKU状态（排除已终止） | 采购订单状态 |
| --- | --- |
| 全部为已完结 | **已入库** |
| 存在未完结的SKU | **部分入库** |
| 全部为已终止（无已完结） | **已取消** |

### 状态转换路径

```
已发货 --> 已入库 : 全部需求SKU入库完结
已发货 --> 部分入库 : 部分需求SKU入库完结
已发货 --> 已取消 : 自动关单且无已发货商品
部分发货 --> 已发货 : 供应商完成剩余发货
```

注意：只能从"已发货"到"部分入库"，不从"部分发货"直接到"部分入库"。部分发货状态下，需求SKU状态变更为已完结时，不触发采购订单状态判定，仅更新商品明细的入库数量和退货数量。

### 业务规则

| 编号 | 规则描述 |
| --- | --- |
| R5-1 | 触发时机：采购订单关联的需求SKU状态变更为"已完结"时 |
| R5-2 | 判定范围：检查该采购订单下所有需求SKU状态（排除已终止），不再比较数量 |
| R5-3 | 全部已完结 → 已入库；存在未完结 → 部分入库 |
| R5-4 | 全部已终止（无已完结） → 已取消 |
| R5-5 | "部分入库/已退货"状态名称统一改为"部分入库" |
| R5-6 | 一个需求SKU关联多个采购单时，每个采购单独立判定 |
| R5-7 | 自动关单场景同样适用SKU状态判定逻辑：已发货部分的需求SKU全部已完结 → 已入库；存在未完结 → 部分入库 |
| R5-8 | 自动关单后，已发货部分的需求SKU状态为"进行中"（既无已完结也无已终止）时，采购订单状态保持"已发货"，等待仓库入库 |

## 功能6：需求生成方式配置化

### 涉及页面

订单履约平台 - 需求基础配置

### 变更说明

原逻辑：需求生成方式写死（现货/POD用缺货计算）

新逻辑：在需求基础配置中，按商品类型（现货、自研、POD）分别配置生成方案，自动生成需求时按配置执行

### 配置项

| 配置位置 | 商品类型 | 可选方案 | 说明 |
| --- | --- | --- | --- |
| 需求基础配置 | 现货 | 方案1：缺货数量 / 方案2：销一采一 |  |
| 需求基础配置 | 自研 | 方案1：缺货数量 / 方案2：销一采一 | （当前不自动生成需求，提前配置） |
| 需求基础配置 | POD | 方案1：缺货数量 / 方案2：销一采一 |  |

每个商品类型只能配置一个方案。

### 方案说明

两种方案均按**供应商维度**聚合，1个供应商=1条需求单，区别在于需求数量的计算方式：

**方案1：缺货数量**
- 需求数量 = 需求数量 - 可用库存 - 在途

**方案2：销一采一**
- 需求数量 = 时间段内该供应商所有订单中该SKU的数量之和
- 不计算可用库存和在途

### 业务规则

| 编号 | 规则描述 |
| --- | --- |
| R6-1 | 需求基础配置中，每个商品类型（现货、自研、POD）可配置生成方案（缺货数量/销一采一），每个类型只能选一个方案 |
| R6-2 | 自动生成需求时，按商品类型读取配置，按对应方案执行 |
| R6-3 | 方案1（缺货数量）：缺货数量 = 需求数量 - 可用库存 - 在途，按供应商维度聚合生成需求单 |
| R6-4 | 方案2（销一采一）：支持手动触发和自动定时两种方式，均按"上次记录时间 ~ 当前时间"拉取增量数据，拉取完成后记录当前时间 |
| R6-5 | 两种方案均按供应商维度聚合，同一供应商的SKU汇总生成一条需求单 |
| R6-6 | 方案2（销一采一）：不计算可用库存和在途 |
| R6-7 | 供应商取默认供应商（isDefault=true），无供应商的SKU单独聚合为一条需求单 |
| R6-8 | 供应商必须在履约平台供应商列表中存在，不存在的SKU不生成需求 |
| R6-9 | 需求单状态默认为"待确认"，需求单内SKU状态默认为"待确认" |
| R6-10 | 拆分规则、字段取值规则、联动规则保持不变（参考525版本PRD 4.2节） |

## 功能7：POD需求完成下单拆分逻辑调整

### 涉及页面

订单履约平台 - 内部商品需求管理

### 变更说明

原逻辑：POD需求点击"完成下单"后，按**收款人**维度拆分生成采购单

新逻辑：
1. POD需求支持自动完成下单（复用5.1.8自动下单逻辑：必填字段都有数据时自动完成下单）
2. 按**供应商 + 采购员 + 是否1688采购**三个维度拆分生成采购单

### 采购单供应商取值变更

采购单的供应商字段：原取收款人 → 新取需求单的供应商。

### 业务规则

| 编号 | 规则描述 |
| --- | --- |
| R7-1 | POD需求支持自动完成下单：自动生成的POD需求，必填字段都有数据时自动完成下单并触发拆分生成采购单（复用5.1.8自动下单逻辑） |
| R7-2 | 点击"完成下单"或自动完成下单后，按供应商 + 采购员 + 是否1688采购三个维度聚合拆分生成采购单 |
| R7-3 | 三个维度均相同的需求SKU，归入同一张采购单 |
| R7-4 | 采购单的供应商字段取需求单的供应商（原取收款人） |
| R7-5 | 拆分后每张采购单的采购员、是否1688采购取对应聚合维度的值 |
| R7-6 | 采购单其他字段（采购价、数量、备货主体、税率等）保持不变 |

### 拆分示例

**场景**：一个需求单内有5个SKU

| SKU | 供应商 | 采购员 | 是否1688 |
| --- | --- | --- | --- |
| SKU001 | 供应商A | 采购员甲 | 否 |
| SKU002 | 供应商A | 采购员甲 | 否 |
| SKU003 | 供应商A | 采购员乙 | 否 |
| SKU004 | 供应商B | 采购员甲 | 是 |
| SKU005 | 供应商B | 采购员甲 | 否 |

**生成结果**：4张采购单

| 采购单 | 供应商 | 采购员 | 是否1688 | 包含SKU |
| --- | --- | --- | --- | --- |
| 采购单1 | 供应商A | 采购员甲 | 否 | SKU001、SKU002 |
| 采购单2 | 供应商A | 采购员乙 | 否 | SKU003 |
| 采购单3 | 供应商B | 采购员甲 | 是 | SKU004 |
| 采购单4 | 供应商B | 采购员甲 | 否 | SKU005 |

### 异常处理

| 场景 | 处理方案 |
| --- | --- |
| 需求单内SKU的供应商或采购员有空值 | 空值作为独立维度参与拆分 |
