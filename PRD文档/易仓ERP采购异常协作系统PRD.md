---

## 1. 需求背景与目标

### 1.1 业务背景
目前仓库在质检 (QC) 和收货环节产生的异常（如不良品、数量差异、单价差异）在易仓 ERP 生成后，缺乏与供应商的数字化协作渠道。目前依赖采购员线下沟通，导致物流跟踪号回填不及时、PO 采购单长期挂账无法结案、运费分摊不清晰。

### 1.2 项目目标
1. **打破信息孤岛**：将易仓 ERP 内部的异常单据（含实物图片）实时同步至订单履约平台门户。
2. **提升协作效率**：供应商可在线回填物流单号和运费，自动同步回写 ERP，无需采购员二次录入。
3. **流程合规化**：针对“终止来货”等涉及订单状态变更的高权操作，建立“供应商申请 -> 采购员审核 -> API 自动结案”的闭环机制。

## 2. 角色与权限

| 角色 | 核心职责 | 门户权限 |
| :--- | :--- | :--- |
| **我司采购员** | 易仓端初步决策、履约平台终审、同步任务监控 | 查看全量数据、审核“终止”申请、手动触发同步任务 |
| **供应商** | 接收采购指令、录入物流及费用信息、提交异常反馈 | 仅查看关联 PO 异常、回填物流号/运费、申请终止来货 |

---

## 3. 业务流程说明

### 3.1 总体业务链路
1. **决策阶段 (易仓)**：采购员在易仓 ERP 对 QC 或收货异常下达初步处理结论（退货、换货等）。
2. **同步阶段 (ETL)**：履约平台定时抓取易仓增量记录，解析 `biz_content`，根据 `po_code` 自动推送给对应供应商。
3. **协作阶段 (门户)**：供应商根据结论填入补发物流单号或申请终止来货。
4. **结案阶段 (回写)**：采购员在门户点击通过后，系统串行调用易仓 Handling 接口及 PO 管理接口，关闭异常单并修正采购单状态。

## 4. 功能需求详细描述

### 4.1 异常数据增量同步
*   **接口依赖**：`qcReceiptList` (QC 异常)、`abnormalReceiptList` (收货异常)。
*   **同步频率**：每 15 分钟/次（需支持后台手动立即拉取）。
*   **路由规则**：必须通过 `supplier_code` 强校验，确保供应商 A 无法看到供应商 B 的数据。
*   **字段解析**：必须提取 `product_img` (图片) 和 `qe_desc` (采购备注) 以供前端展示。

### 4.2 供应商处理门户
*   **换货/退回处理**：
    *   供应商填入 `logistics_tracking_number` (必填) 和 `resend_freight` (补发运费)。
    *   点击提交后，系统自动回写易仓，并将物流号挂载至原始 PO。
*   **终止来货申请**：
    *   若供应商无法履约，需选择“终止来货”并填写具体原因。
    *   **业务约束**：提交后单据状态转为“待采购审核”，暂时不回写易仓。

### 4.3 采购员审批工作台
*   **终止申请审核**：
    *   采购员核对供应商理由。
    *   **财务逻辑**：审核时必须选择 `refund_type` (退款类型)，确定货款、运费、税金的退回比例。
*   **API 联动回写**：
    *   审核通过后，系统依次调用 `handlingReceivingExceptions` 和 `purchaseForceCompletion`，实现 ERP 内采购单强行结案。

## 5. API 集成规格与逻辑 (Data Contract)

| 场景 | 核心接口 | 关键回传字段 | 逻辑备注 |
| :--- | :--- | :--- | :--- |
| **换货补发** | `handlingQcExceptions` | `operation_type=6`, `tracking_no` | 结案 QC 异常单 |
| **物流追踪** | `syncPurchaseTrackingNote` | `tracking_no`, `supplier_method_id` | 将单号同步至 PO 跟踪记录 |
| **收货多出** | `handlingReceivingExceptions` | `type=2`, `re_assumer` (责任方) | 必须明确责任归属 |
| **终止来货** | `purchaseForceCompletion` | `po_code`, `refund_type`, `note` | 底层 PO 强行结案，平账财务 |

---

## 6. UI/UX 交互要求

1. **可视化证据**：QC 详情页必须支持 `product_img` 的悬停放大，方便供应商核实不良品项。
2. **动态表单**：
    *   当 `type=2` (多发) 时，强制显示“责任方”单选框。
    *   当 `operation_type=6` (换货) 时，强制显示“物流号”输入框。
3. **反馈感知**：回写易仓时显示进度条，若 API 报错（如 `sign` 错误或单据已手动关闭），需准确透传易仓的 `message` 内容。

---

## 7. 非功能性需求

1. **安全性**：所有 API 请求必须使用 `AES-128-CBC` 签名，`biz_content` 需严格执行转义序列化。
2. **鲁棒性**：若 PO 强关接口失败，异常单处理接口需回滚或允许重试，防止单据状态在两个系统间不一致。
3. **审计要求**：履约平台需存储所有回写报文 (Request/Response)，以备财务审计查对货款抵扣。

---

## 8. 验收准则 (Acceptance Criteria)

*   [ ] **同步性**：易仓更新异常处理意见后，履约平台应在 30 分钟内同步更新展示。
*   [ ] **一致性**：门户回填的物流号必须能在易仓 ERP 采购单的“跟踪记录”中查看到。
*   [ ] **结案性**：采购员在门户点击“终止通过”后，易仓内的原始 PO 状态应自动变更为“强制完成”。
*   [ ] **权限性**：供应商无法通过 URL 拼接等方式越权查看其他厂商的异常单。
